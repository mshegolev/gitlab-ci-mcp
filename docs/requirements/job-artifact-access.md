# Требование: чтение артефактов GitLab CI job через MCP

**Статус:** требование для реализации  
**Контекст:** расследование упавших CI/Gatling-прогонов  
**Область:** только чтение артефактов; запуск, повтор и изменение pipeline не входят в задачу.

## Проблема

MCP позволяет получить список job и trace через `gitlab_get_job_log`, но не позволяет посмотреть artifacts завершившейся job. Trace может быть усечён, а существенные диагностические данные часто сохраняются в отдельных файлах: JSON-сводках, receipts, Allure results и вложениях. Из-за этого нельзя проверить результат job целиком и отличить отсутствующий артефакт от отсутствия доступа к нему.

## Цель

Дать агенту возможность обнаружить артефакты конкретной GitLab CI job, прочитать выбранный текстовый файл и использовать полученные данные для расследования без скачивания всего архива в контекст.

## Требуемый интерфейс MCP

Добавить read-only инструменты:

1. **`gitlab_list_job_artifacts`** — перечисляет файлы внутри artifact archive job: относительный путь, размер и тип/признак каталога, если это можно надёжно определить.
2. **`gitlab_get_job_artifact`** — получает содержимое одного файла по относительному пути из artifacts job.

Оба инструмента принимают:

- `job_id` — обязательный положительный числовой ID job;
- `project_path` — необязательный путь проекта, использующий существующее разрешение проекта и правила scoping MCP;
- для чтения файла: `artifact_path` — обязательный относительный путь внутри архива;
- для чтения файла: `max_bytes` — необязательный лимит ответа с безопасным верхним пределом.

Точная форма аргументов и имена полей результата должны соответствовать существующим моделям, аннотациям и structured output проекта.

## Поведение

- Использовать GitLab CI Jobs API для job artifacts. Сначала проверить поддерживаемый GitLab endpoint и поведение `python-gitlab` для закреплённой проектом версии; не предполагать, что архив доступен через trace API.
- Список артефактов должен позволять выбрать один файл для последующего чтения. Если установленный API не предоставляет список файлов, MCP должен безопасно прочитать ZIP-каталог архива в памяти/временном потоке, вернуть только метаданные и не включать бинарное содержимое.
- Чтение файла должно возвращать текст только для поддерживаемых текстовых форматов с корректной UTF-8-декодировкой. Для бинарных, слишком больших или некорректно декодируемых файлов возвращать структурированное объяснение и, где возможно, метаданные (размер, тип), не выдавая повреждённый текст.
- Ответ ограничивается `max_bytes` и абсолютным серверным пределом. Если файл усечён по лимиту, явно указать `truncated=true`, полный размер и число возвращённых байт.
- Сохранять обычную обработку ошибок MCP: различать job/project not found, отсутствие artifacts у job, отказ GitLab в доступе, истёкший/недоступный artifact и ошибки rate limit/сервера. Не превращать «нет доступа» или «файл не найден» в пустой успешный ответ.
- Инструменты должны быть отмечены как read-only, без destructive effects и идемпотентные.
- Использовать тот же клиент GitLab, project scoping, аутентификацию и обработку ошибок, что и остальные CI-инструменты. Не вводить отдельный токен и не ослаблять существующие проверки доступа.

## Безопасность и ограничения

- Никогда не писать токен или заголовки авторизации в результат инструмента, логи и сообщения об ошибках.
- Не скачивать и не возвращать весь архив как base64 или единый большой текстовый ответ.
- При разборе ZIP проверять пути: отвергать абсолютные пути, `..` и другие пути, выходящие за корень архива; не извлекать файлы на постоянный диск.
- Не читать URL, переданный пользователем, и не делать произвольные HTTP-запросы: доступ только к artifacts указанной job через настроенный GitLab API-клиент.
- Не добавлять автоматическую маскировку, которая меняет содержимое отчёта незаметно. Если проект имеет общую функцию редактирования секретов, применять её по существующим правилам и сообщать, что содержимое было отредактировано.

## Критерии приёмки

1. По валидным `project_path` и `job_id` список показывает имена файлов и размеры из архива job без выдачи их содержимого.
2. По `artifact_path` MCP возвращает содержимое небольшого UTF-8 текстового файла и метаданные job/файла.
3. Большой текстовый файл ограничен лимитом; ответ явно показывает усечение и полный размер.
4. Отсутствующие artifacts, отсутствующий файл, несуществующая job, запрет доступа и некорректный путь различаются и дают понятный структурированный результат/ошибку.
5. Бинарный файл не превращается в нечитаемый текст и не возвращается целиком.
6. ZIP entry с абсолютным путём или `..` не извлекается и не читается.
7. Для вызовов проверяются `project_path` scoping, `readOnlyHint`, структурированный ответ, обработка ошибок и отсутствие утечки токена.
8. Тесты используют mock GitLab API и фикстуры ZIP; тесты не обращаются к рабочему GitLab и не требуют настоящих секретов.

## Вне объёма

- Скачать архив artifacts пользователю как файл.
- Читать artifacts pipeline-level, job trace или repository files через новый общий механизм.
- Запускать pipeline/job, повторять job, менять artifacts, удалять их или менять сроки хранения.
- Интерпретировать содержимое Allure/Gatling отчётов отдельной бизнес-логикой. MCP предоставляет файл; анализ выполняет вызывающий агент.

## Сценарий проверки

Для упавшей Gatling job агент вызывает `gitlab_list_job_artifacts`, находит, например, JSON-диагностику или Allure result, затем вызывает `gitlab_get_job_artifact` только для выбранного файла. Если архива или нужного файла нет либо доступ запрещён, MCP сообщает конкретную причину, чтобы расследование не трактовало отсутствие данных как успешный результат.
